# เอกสารความต้องการระบบ (Technical Specification)
## ระบบเคลียร์เงินทดลองจ่าย (Clear Advance Form: AP-3)

เอกสารฉบับนี้จัดทำขึ้นเพื่อกำหนดความต้องการทางเทคนิค (Technical Specification) และรายการพัฒนาซอฟต์แวร์ (Development Backlog) สำหรับ**ระบบแบบฟอร์มเคลียร์เงินทดลองจ่าย (Clear Advance Form: AP-3)** เพื่อให้ทีมพัฒนาโปรแกรม (Developers) ใช้เป็นมาตรฐานในการปรับปรุง แก้ไข และพัฒนาต่อยอดระบบให้ตรงตามเงื่อนไขด้านบัญชีและการควบคุมภายในขององค์กร

---

## 1. ข้อกำหนดด้านส่วนประสานงานผู้ใช้และฟังก์ชันทั่วไป (UI & General Functions)

### 1.1 การแก้ไขข้อผิดพลาดการแสดงผลเอกสารแนบ (PDF Attachment Bug Fix)
* **ปัญหาปัจจุบัน**: หน้าจอผู้ดูแลระบบของแผนกบัญชี (Accounting / Acc Account Page) ไม่สามารถเปิดแสดงผลหรืออ่านไฟล์แนบประเภท PDF ที่พนักงานอัปโหลดเข้ามาในระบบได้
* **ข้อกำหนดทางเทคนิค**:
  * พัฒนาและแก้ไขให้ส่วนแสดงผลเอกสารแนบ (Document Viewer Node) รองรับการเปิดอ่าน ปรับขนาด และดาวน์โหลดไฟล์สกุล `.pdf` ได้โดยตรงบนเบราว์เซอร์โดยไม่เกิดข้อผิดพลาดในการโหลดข้อมูล (Rendering Error)

### 1.2 ระบบการสั่งพิมพ์ใบเบิกเคลียร์เงิน (AP-3.1 Print-out Function)
* **ข้อกำหนดทางเทคนิค**:
  * พัฒนาปุ่มคำสั่ง **"พิมพ์เอกสาร (Print)"** บนหน้าจอใบเบิกเคลียร์เงิน (AP-3.1)
  * ออกแบบฟอร์แมตหน้าสั่งพิมพ์ (Print CSS / Media Query) ให้จัดหน้าเอกสารอย่างสวยงามและเป็นระเบียบเมื่อพิมพ์ออกทางเครื่องพิมพ์ (Printer) หรือบันทึกเป็น PDF
  * เอกสารที่พิมพ์ออกมาจะต้องแสดงรายการข้อมูลสำคัญครบถ้วนเพื่อใช้เป็นหลักฐานทางกายภาพ (Hard Copy) สำหรับให้พนักงานเซ็นชื่อรับรอง และแนบใบเสร็จรับเงิน/ใบกำกับภาษีฉบับจริงส่งมอบให้แผนกบัญชีตามขั้นตอนการตรวจรับเงินมาตรฐาน

## 2. ระบบสแกนเอกสารและวิเคราะห์ข้อมูลด้วย AI (AI OCR Integration)

เพื่อลดขั้นตอนการป้อนข้อมูลด้วยมือ (Manual Input) และลดข้อผิดพลาดในการบันทึกบัญชี ระบบต้องผสานการทำงานร่วมกับระบบสแกนเอกสารอัจฉริยะ (AI OCR) โดยมีรายละเอียดดังนี้:

### 2.1 ปรับปรุงการจัดวางตำแหน่งฟิลด์แนบเอกสาร (Layout Adjustment)
* **ข้อกำหนดทางเทคนิค**: ปรับปรุงโครงสร้างหน้าจอ (Layout) โดยย้ายตำแหน่งกล่องอัปโหลดเอกสารใบเสร็จและใบกำกับภาษีขึ้นไปจัดวางไว้ที่**ส่วนบนสุดของฟอร์ม** (ก่อนถึงตารางการกรอกรายการค่าใช้จ่ายจริง) เพื่อให้สอดคล้องกับพฤติกรรมการใช้งานที่ต้องอัปโหลดเอกสารก่อนการป้อนข้อมูล

### 2.2 ระบบสแกนและนำเข้าข้อมูลตารางอัตโนมัติ (AI Receipt OCR)
* **กระบวนการทำงาน (Workflow)**:
  1. พนักงานทำการอัปโหลดไฟล์ใบเสร็จ (รองรับ PDF, PNG, JPG)
  2. พนักงานกดปุ่ม **"อ่านรายการจากไฟล์แนบ"**
  3. ระบบจะส่งไฟล์เข้าสู่กระบวนการวิเคราะห์ข้อมูลด้วย AI (OCR Model)
  4. ระบบประมวลผลเสร็จสิ้นและแสดงข้อมูลที่สแกนได้ในรูปแบบ **Pop-up เพื่อให้พนักงานตรวจสอบและแก้ไขความถูกต้อง** ก่อนกดยืนยันป้อนข้อมูลลงตารางค่าใช้จ่ายจริง
* **เงื่อนไขและข้อกำหนดในการบันทึกข้อมูล (Business Rules)**:
  * **อัตราส่วนการบันทึกเอกสาร**: กำหนดให้ใช้เงื่อนไข **1 เอกสารใบเสร็จ (Invoice/Receipt) = 1 แถวรายการในตาราง (1:1)**
  * **กรณีใบเสร็จมีรายการย่อยจำนวนมาก (Multiple Lines)**: 
    * ให้ระบบ AI คัดเลือกคำอธิบายรายการ (Description) ของรายการย่อยที่มียอดเงินที่สูงที่สุดในใบเสร็จนั้น มาเป็นตัวแทนกรอกลงในคอลัมน์คำอธิบายรายการ (Description Column)
    * ดึงยอดมูลค่าเงินรวมสุทธิ (Total Amount) ของใบเสร็จนั้นมากรอกลงในคอลัมน์จำนวนเงินรวม
  * **ระบบแนะนำรหัสบัญชีอัจฉริยะ (AI GL Code Suggestion)**:
    * พัฒนาให้ AI ทำการวิเคราะห์คำอธิบายรายการจากหน้าใบเสร็จ แล้วประเมินรหัสบัญชีแยกประเภท (GL Account Code) ที่สัมพันธ์กับประเภทค่าใช้จ่ายนั้นๆ มากรอกแสดงเพื่อเป็นตัวเลือกแนะนำ (Suggestion) ให้ผู้ใช้พิจารณาตรวจสอบความถูกต้อง
  * **ระบบสแกนสลิปโอนคืน (Refund OCR)**:
    * สำหรับกรณีที่พนักงานใช้จ่ายเงินเหลือและต้องโอนเงินคืนเข้าบัญชีบริษัท ให้พัฒนาระบบสแกนสลิปโอนเงินคืน (Bank Transfer Slip OCR) โดยระบบต้องสามารถอ่านและดึงข้อมูล **"วันที่โอนเงิน" (Transfer Date)** และ **"ยอดเงินที่โอน" (Transfer Amount)** มากรอกแสดงในฟอร์มเคลียร์เงินคืนได้โดยอัตโนมัติ

## 3. การควบคุมรหัสบัญชีแยกประเภทและสาขา (Branch & GL Account Control)

ระบบต้องควบคุมความสัมพันธ์ระหว่างรหัสหน่วยงาน/สาขา กับรหัสบัญชีค่าใช้จ่าย เพื่อป้องกันการลงบันทึกบัญชีผิดพลาด ดังนี้:

### 3.1 หน้าจอควบคุมสิทธิ์การเบิกจ่ายรหัสบัญชี (Maintain Page for GL Accounts)
* **ข้อกำหนดทางเทคนิค**:
  * พัฒนาหน้าจอตั้งค่าสิทธิ์แยกต่างหากสำหรับเจ้าหน้าที่แผนกบัญชีบริหารจัดการระบบ (Maintain Page)
  * เจ้าหน้าที่บัญชีสามารถเข้ามาตั้งค่า ติ๊กเลือก หรือแก้ไขรายชื่อรหัสบัญชีแยกประเภท (GL Accounts) ที่ระบบอนุญาตให้พนักงานดึงไปใช้งานในระบบใบเบิกได้เท่านั้น (จำกัดสิทธิ์การเลือกผูกบัญชีเพื่อลดความสับสนของพนักงาน)

### 3.2 ระบบกรองความสัมพันธ์ระหว่างสาขาและรหัสบัญชี (Conditional Selector Control)
* **สลับตำแหน่งฟิลด์ข้อมูล**: ปรับหน้าจอตารางค่าใช้จ่ายโดย**สลับตำแหน่งคอลัมน์การเลือก "สาขา" ขึ้นมาแสดงก่อนคอลัมน์ "รหัสบัญชี"**
* **เงื่อนไขตัวกรองบัญชีแยกประเภท (Conditional Filtering Rules)**:
  * หากผู้ใช้งานทำการเลือกสาขาเป็น **"สำนักงานใหญ่ (HQ)"**: ระบบจะต้องกรองและแสดงผลตัวเลือกรหัสบัญชีเฉพาะรายการที่ **ไม่มีคำลงท้ายว่า "สาขา"** เท่านั้น
  * หากผู้ใช้งานทำการเลือกสาขาเป็น **"รหัสสาขา (PC)"** (เช่น PC 10xx, PC 20xx): ระบบจะต้องกรองและแสดงผลตัวเลือกรหัสบัญชีเฉพาะรายการที่ **มีคำลงท้ายว่า "สาขา"** เท่านั้น
* **ข้อกำหนดปุ่มเลือกสาขา (Branch Selector)**:
  * ข้อมูลสาขาที่นำมาแสดงให้เลือก ต้องเป็นข้อมูลเฉพาะสาขาที่ยังมีสถานะเปิดใช้งานอยู่จริง (**Active**) ในฐานข้อมูลเท่านั้น
  * ปรับกล่องข้อความตัวเลือก (Selector) ให้เป็นประเภท **Dropdown ค้นหาได้ (Searchable Dropdown)** เพื่อเพิ่มความสะดวกรวดเร็วในการค้นหารหัสสาขาโดยพนักงานพิมพ์ระบุคำค้นหาได้โดยตรง

## 4. โครงสร้างและการบันทึกข้อมูลเพื่อเชื่อมต่อ ERP (Clear Advance ERP Interface)

เมื่อแบบฟอร์ม AP-3 ผ่านกระบวนการอนุมัติสิ้นสุด (Approved) ระบบจะทำการส่งข้อมูล Interface เข้าสู่ระบบ ERP เพื่อล้างยอดเงินทดลองจ่ายเดิมตามโครงสร้างข้อมูล ดังต่อไปนี้:

| ฟิลด์ข้อมูล (Field Name) | ค่าเริ่มต้น / เงื่อนไขทางเทคนิค (Specification & Mapping Logic) |
| :--- | :--- |
| **Posting Date** | • กรณีพนักงานโอนเงินคืนบริษัท (Refund): ให้ยึดวันที่โอนเงินตามหลักฐานใบสลิป<br>• กรณีบริษัทจ่ายคืนเพิ่มให้พนักงาน (Payment): ให้ยึดตามวันที่ที่แผนกการเงินระบุบันทึกจ่ายจริงในระบบ |
| **External Document** | ส่งข้อมูลเป็น **"รหัสพนักงาน (Employee ID)"** เท่านั้นเพื่อใช้ตรวจสอบอ้างอิง |
| **Document Type** | • ระบุเป็นค่า `Refund` หากยอดจ่ายจริงน้อยกว่ายอดเบิก (พนักงานคืนเงินเหลือโอนเข้าบริษัท)<br>• ระบุเป็นค่า `Payment` หากยอดจ่ายจริงมากกว่ายอดเบิก (บริษัทจ่ายส่วนเกินคืนพนักงาน) |
| **Bank Line (บัญชีธนาคาร)** | • ลงบันทึกรายการฝั่ง **เดบิต (Debit)** สำหรับประเภท Refund<br>• ลงบันทึกรายการฝั่ง **เครดิต (Credit)** สำหรับประเภท Payment |
| **Expense Line (ค่าใช้จ่าย)** | บันทึกรายการฝั่ง **เดบิต (Debit)** ด้วยจำนวนเงินค่าใช้จ่ายสุทธิก่อนรวมภาษีมูลค่าเพิ่ม (Before VAT Amount)<br>• **Format คำอธิบาย (Description)**:<br>  `[เลขที่ ADV] + "เบิก" + "เคลียร์เงินทดลอง" + [ชื่อพนักงานที่เคลียร์] + [รายละเอียดเอกสาร]` |
| **Mjus Indicator** | บันทึกค่าลงตัวเป็นอักษร **"MS"** เสมอ หากกรณีที่วันที่เกิดขึ้นจริงบนใบเสร็จเอกสาร (Document Date) เป็นวันที่ย้อนหลังก่อนเดือนที่ระบบทำการโพสต์บันทึกบัญชีลง ERP (Document Date < Posting Date Month) |
| **VAT Line (ภาษีซื้อ)** | (กรณีใบเสร็จมีรายการ VAT) บันทึกรายการบัญชี **"ภาษีซื้อยังไม่ถึงกำหนด"** เป็นค่าเริ่มต้น พร้อมส่งรายละเอียดภาษีประกอบดังนี้:<br>• Posting Type: `purchase`<br>• VAT Code: `VATHO` หรือ `FVAT` (ตามแต่กรณีที่ผู้ใช้เลือก)<br>• Document Date: วันที่เกิดขึ้นจริงบนเอกสารสลิป/ใบเสร็จตัวจริง<br>• ข้อมูลผู้เสียภาษี: เลขประจำตัวผู้เสียภาษี และชื่อคู่ค้าผู้เสียภาษีที่ AI สแกนได้<br>• ยอดเงินภาษี: มูลค่าเงินภาษีมูลค่าเพิ่มตามใบเสร็จจริง |
| **WHT & Clear Advance Line** | **ส่งค่าเป็น 0 บาท (ศูนย์บาท) ทั้งคู่เสมอ** เพื่อให้เจ้าหน้าที่แผนกบัญชีเป็นผู้ดำเนินการ Manual ในระบบ ERP ในการเคลียร์ยอดล้างรายการเวนเดอร์และกลับรายการบัญชีเดิม (AP-2) ด้วยตนเอง<br>*(ส่งผลให้ในขั้นตอนการแสดงตัวอย่างข้อมูล (Preview Stage) บนหน้า ERP Portal ยอดเงินเดบิตและเครดิตจะไม่ Balance กันตามธรรมชาติของข้อกำหนดนี้)* |

### 4.1 ระบบจัดเกรดประเภทภาษีหัก ณ ที่จ่ายเบื้องต้น (WHT Classification Assistant)
* **ฟังก์ชันช่วยเหลือของระบบ**: พัฒนาระบบให้วิเคราะห์เลขประจำตัวผู้เสียภาษีกับระบบ DBD (กรมพัฒนาธุรกิจการค้า) เบื้องต้น หากตรวจพบชื่อองค์กรในกลุ่มนิติบุคคลให้ระบุและแนะแนวทางเลือกภาษีเป็นประเภท **ภ.ง.ด. 53** หากเป็นบุคคลทั่วไปให้ระบุเป็น **พ.ง.ด. 3** เพื่อช่วยเหลือการทำเอกสาร แต่อย่างไรก็ตามค่าทางการเงินที่ส่งเข้า Interface ERP จะต้องมีมูลค่าเป็น 0 และระบุรหัส Vendor ตั้งต้นเป็นเลข 3 เป็นหลักก่อนตามเงื่อนไขทางบัญชี
