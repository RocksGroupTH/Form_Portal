# เอกสารความต้องการระบบ (Technical Specification & Development Backlog)
## ระบบ Advance Payment (AP-2, AP-3) และระบบจองตั๋ว/ที่พักและเบี้ยเลี้ยง (AP-17)

---

## 1. ระบบขออนุมัติเงินทดลองจ่าย (Advance Form: AP-2)

### 1.1 การปรับปรุงฟิลด์ข้อมูลบนหน้าฟอร์ม (Form Schema Improvements)
*   **รหัสสาขา (Branch Code)**:
    *   เพิ่มช่องกรอกข้อมูลประเภท **Numeric ความยาวคงที่ 4 หลัก** สำหรับระบุรหัสสาขา (Branch Code) ของรายการเบิกจ่าย
*   **เลขที่บัญชี (Account Number)**:
    *   ปรับปรุง Input Control ให้รองรับและจำกัดเฉพาะค่าที่เป็น **Numeric** (ตัวเลข) เสมอ เพื่อป้องกันข้อผิดพลาดในการนำเข้าข้อมูลประเภท Text
*   **เงื่อนไขการตรวจสอบวันที่ (Date Validation Rules)**:
    *   **วันที่ต้องการเริ่มใช้เงิน**: ต้องกำหนดให้ผู้ใช้สามารถระบุได้ตั้งแต่วันปัจจุบันไปจนถึงวันในอนาคตเท่านั้น (Validation: `Date >= Current_Date`)
    *   **วันที่ส่งคืน/เคลียร์เงินคืน (Clearing Date)**: กำหนดให้ระบบคำนวณและจำกัดไม่ให้เกิน **30 วัน** นับจากวันที่เริ่มต้นใช้เงิน (Validation: `Clearing_Date - Start_Date <= 30 Days`)

### 1.2 การคำนวณอัตราแลกเปลี่ยน (Foreign Currency Management)
*   กรณีที่ทำรายการเบิกจ่ายเป็นสกุลเงินต่างประเทศ ระบบต้องเชื่อมโยงข้อมูลกับระบบธนาคารแห่งประเทศไทย (BOT) เพื่อดึง **อัตราแลกเปลี่ยนย้อนหลังล่าสุดของวันทำการก่อนหน้า (BOT Rate - Previous Working Day)** มาใช้เป็นค่าอ้างอิงและคำนวณมูลค่าเป็นยอดเงินบาทโดยอัตโนมัติ

### 1.3 สายการอนุมัติและขั้นตอนการทำงาน (Approval Workflow Rules)
*   ปรับเปลี่ยนเกณฑ์การส่งเอกสารเข้าสายอนุมัติโดยยึดเกณฑ์ยอดเงินเบิกจ่ายดังนี้:
    *   **ยอดเงิน <= 30,000 บาท**: ส่งไปตรวจสอบและอนุมัติที่ **พี่เกล**
    *   **ยอดเงิน > 30,000 บาท**: ส่งไปตรวจสอบและอนุมัติที่ **พี่แน็ก**

### 1.4 การแก้ไขข้อผิดพลาดในการป้อนข้อมูลแทนผู้อื่น (On-Behalf Filing Bug Fix)
*   **คำอธิบายปัญหา**: เกิดบั๊กกรณีเจ้าหน้าที่กรอกฟอร์มแทนพนักงานหลายคนในวันเดียวกัน โดยหลังจากกดบันทึกพนักงานคนแรก (เช่น นาย A) ระบบจะทำการล็อกสิทธิ์ไม่ให้เลือกวันที่สำหรับพนักงานคนถัดไป (เช่น นาย B)
*   **แนวทางแก้ไข**: ปรับปรุงสถานะการจัดเก็บค่าและการล้างหน่วยความจำชั่วคราว (Reset State) ของโปรแกรมบนหน้าจอเบิกจ่ายแทนให้ทำงานแบบอิสระในแต่ละเซสชัน (Independent Form Contexts) เพื่อให้สามารถเลือกวันกรอกใหม่ได้ทุกครั้งโดยไม่มีการค้างค่าเงื่อนไขเดิม

### 1.5 ระบบการจับคู่และสร้างข้อมูลผู้ขาย (ERP Vendor Matching & Creation)
*   **การจับคู่ข้อมูล (Vendor Matching)**: ปรับปรุงการส่งออกข้อมูลหลังบ้านเพื่อการ Interface เข้าสู่ ERP โดยเปลี่ยนจากการแมปข้อมูลด้วยชื่อพนักงาน (Display Name) มาเป็น **"รหัสพนักงาน" (Employee Code)** เป็นเกณฑ์หลัก (Primary Key) ในการจับคู่ข้อมูล เพื่อหลีกเลี่ยงประเด็นเรื่องการสะกดชื่อวรรคตอนผิดพลาด
*   **ระบบสร้างการ์ดพนักงานใหม่ (Automated Vendor Card Creation)**:
    *   หากระบบไม่พบชื่อหรือรหัสพนักงานในฐานข้อมูล ERP (เคสพนักงานเข้าใหม่) ระบบต้องเปิดช่องทางให้เจ้าหน้าที่บัญชีสามารถคลิก **"สร้าง Vendor Card ใหม่"** จากหน้าจอนี้ส่งเข้าสู่ ERP ได้ทันที
    *   รายละเอียดที่ต้องระบุสำหรับการสร้าง Vendor Card (กำหนดข้อมูลบังคับ 3-4 รายการ):
        *   `Vendor Posting Group` (เช่น General Posting Group)
        *   `Bank Account Details` (รายละเอียดเลขที่บัญชีและสาขาธนาคารของพนักงาน)
    *   **การแมปชื่อผู้ค้าภาษาไทย (Thai Vendor Mapping)**: หากระบบค้นพบรายการข้อมูลชื่อผู้ขายใน ERP เป็นภาษาไทย ให้ระบบทำการตรวจสอบและแมปข้อมูลให้โดยอัตโนมัติ

### 1.6 ข้อกำหนดวันทำจ่ายและการล็อกสิทธิ์ (Payment Calendar Control)
*   **Payment Date**: ปรับให้ระบบล็อกปฏิทินให้สามารถระบุเลือกวันทำจ่ายได้เฉพาะ **"วันศุกร์สัปดาห์ที่ 2 และวันศุกร์สัปดาห์ที่ 4" ของเดือน** หรือวันศุกร์ในอนาคตที่ระบบอนุมัติเปิดให้ทำจ่ายเท่านั้น
*   **การล็อกสิทธิ์ทำจ่าย**: กรณีรายการส่งเบิกข้อมูลพนักงานใดที่ตรวจพบว่า **ยังไม่สามารถระบุ/ไม่มีรหัส Vendor ในระบบบัญชี** ระบบต้องล็อกปุ่มส่งทำจ่ายเพื่อไม่ให้อนุมัติรายการดำเนินการต่อได้จนกว่าจะแก้ไขข้อมูลให้สมบูรณ์

### 1.7 การปรับปรุงหน้าจอเจ้าหน้าที่บัญชี (AP Officer UI Interface)
*   เอาช่องระบุ **PV No. (เลขที่สำคัญจ่าย)** และข้อความระบุคำว่า **"เช็ค"** ออกจากหน้าต่างจัดการฟอร์มนี้
*   **แนวทางการทำงานแบบใหม่**: ปรับให้เจ้าหน้าที่บัญชีระบุเพียงตัวแปร **Payment Date** และคลิกปุ่มดำเนินการอนุมัติ (Action) เท่านั้น เนื่องจากระบบจะดึงรหัสใบสำคัญ PV จากระบบ ERP มาแสดงผลให้อัตโนมัติภายหลังจากกระบวนการส่งออกและ Interface ข้อมูลเข้าสู่ ERP Portal สำเร็จเรียบร้อยแล้ว

## 2. ระบบเคลียร์เงินทดลองจ่าย (Clear Advance Form: AP-3)

### 2.1 การแสดงผลไฟล์แนบและความเข้ากันได้ (Attachment Compatibility)
*   แก้ไขข้อจำกัดบนหน้าจอผู้ตรวจสอบแผนกบัญชี (**Acc Account Page**) ให้สามารถรองรับการโหลด เปิดดู และตรวจสอบความถูกต้องของไฟล์รูปภาพและเอกสารประเภท **PDF** ได้อย่างสมบูรณ์แบบไม่เกิดข้อผิดพลาดในการโหลด

### 2.2 ระบบตรวจสอบและอ่านข้อมูลเอกสารด้วย AI (OCR Receipt Integration)
*   **สลับอินเตอร์เฟสอัปโหลด**: ปรับสัดส่วน Layout หน้าจอโดยย้ายกล่องฟังก์ชันแนบไฟล์ใบเสร็จ/ใบกำกับภาษีขึ้นไปอยู่ **ด้านบนสุดของหน้าต่างการกรอกข้อมูล**
*   **ปุ่มดึงรายการอัตโนมัติ**: เพิ่มปุ่ม **"อ่านรายการจากไฟล์แนบ"** เพื่อให้ระบบสั่งการ AI สแกนเอกสารจริงที่อัปโหลดไปแล้ว
*   **ป๊อปอัปตรวจสอบ (Verification Pop-up)**: เมื่อ AI สแกนและตรวจวิเคราะห์เนื้อหาเสร็จสิ้น ให้ระบบแสดงผลรายการข้อมูลที่ได้ผ่านกล่องข้อความเตือน (Pop-up Widget) ให้ผู้ใช้งานตรวจสอบ ความถูกต้อง แก้ไขเพิ่มเติมให้ถูกต้อง แล้วจึงกด "ยืนยันบันทึก" เพื่อแปลงข้อมูลลงสู่ตารางรายการค่าใช้จ่ายจริงด้านล่าง
*   **เงื่อนไขและรูปแบบการแปลงข้อมูลตาราง (Data Mapping Rules)**:
    *   **สัดส่วนแถว**: กำหนดโครงสร้าง **1 เลขที่ใบเสร็จ (Invoice No.) = 1 แถวรายการข้อมูล** เสมอ
    *   **รายการหลายบรรทัด (Multiple Lines)**: หากสแกนพบใบเสร็จที่มีรายการย่อยหลายรายการ ให้ AI สรุปประมวลผลดึงคำอธิบาย (Description) ของรายการที่มียอดมูลค่าการเบิกสูงสุดมาแสดงเป็นตัวแทนของชื่อรายการ แต่อย่างไรก็ตาม **ให้ดึงผลรวมมูลค่าเงินทั้งหมด (Total Value) มาบันทึกในช่องช่องยอดเบิกจ่ายเงิน** ของแถวรายการนั้น
    *   **คำแนะนำรหัสบัญชีอัจฉริยะ (GL Account Code Suggestion)**: พัฒนาให้ AI วิเคราะห์บริบทของข้อความ Description บนใบเสร็จ และเสนอแนะแสดงค่าของ **รหัสบัญชีค่าใช้จ่าย** ที่ตรงกันและถูกต้องมากที่สุดแสดงขึ้นมาให้ผู้ใช้ตรวจสอบความถูกต้องตั้งแต่ขั้นตอนพรีวิวบน Pop-up

### 2.3 การวิเคราะห์ข้อมูลหักภาษี ณ ที่จ่าย (Withholding Tax: WHT Analysis)
*   **ระบุประเภท พ.ง.ด. อัตโนมัติ**: ระบบต้องทำการอ่านเลขประจำตัวผู้เสียภาษี (Tax ID) บนหน้าเอกสารเพื่อนำไปตรวจสอบเบื้องต้นกับคลังข้อมูล หรือฐานข้อมูลกรมพัฒนาธุรกิจการค้า (DBD)
    *   หากระบบตรวจพบข้อมูลเป็น **นิติบุคคล**: กำหนดเงื่อนไขส่งออกไปพิจารณาเป็นแบบ **พ.ง.ด. 53**
    *   หากตรวจสอบไม่พบข้อมูลนิติบุคคล: กำหนดเงื่อนไขส่งออกพิจารณาเป็นแบบ **พ.ง.ด. 3**
*   **ข้อจำกัดระยะเริ่มต้นด้านระบบ Interface**: เนื่องจากในปัจจุบันระบบข้อมูลหลังบ้านยังอยู่ระหว่างการพัฒนา ให้กำหนดให้ระบบทำการส่งออกมูลค่าของภาษีหัก ณ ที่จ่าย (WHT) และ ยอดเคลียร์บัญชีเวนเดอร์ใบเบิกเดิม (Clear Advance) เป็น **ยอดคงที่ 0 บาท** เข้าสู่ระบบ ERP เสมอ เพื่อให้เป็นหน้าที่ของเจ้าหน้าที่ตรวจสอบบัญชีดำเนินการเคลียร์ตัดบัญชีและล้างเวนเดอร์ (Manual Match & Clear) ด้วยตนเองผ่านเครื่องมือบนระบบ ERP ต่อไป

### 2.4 การเชื่อมโยง "สาขา" และ "รหัสบัญชี" (Branch & Account Code Mapping Control)
*   **หน้าตั้งค่าสำหรับผู้ดูแล (Account Code Maintain Page)**:
    *   พัฒนาหน้าจอควบคุมแยกต่างหาก (Maintain Page) เพื่อให้ฝ่ายบัญชีสามารถเลือกทำเครื่องหมายกำหนดและจัดการรหัสบัญชีแยกประเภท (GL Accounts) ที่บริษัทอนุญาตให้พนักงานดึงไปเป็นตัวเลือกกรอกเบิกเคลียร์ตามหมวดหมู่ได้
*   **การปรับปรุงลำดับฟิลด์ตัวเลือก (Interface Sequence Update)**:
    *   **ย้ายฟิลด์ "สาขา" (Branch Selector) ขึ้นมาไว้ลำดับแรก**ของการกรอกข้อมูลในแถวตาราง เพื่อบังคับให้ระบุสาขาก่อน จากนั้นระบบจึงจะใช้ข้อมูลสาขานี้ไปส่งฟิลเตอร์คัดเลือกและแนะนำตัวรหัสบัญชีที่อนุญาตต่อไป
*   **เงื่อนไขตัวกรองบัญชีตามระดับสาขา (Data Filtering Rules)**:
    *   กรณีผู้ใช้เลือกเป็น **สำนักงานใหญ่ (HQ)**: ระบบทำการแสดงรายการรหัสบัญชี (Account Code) ให้เลือกเฉพาะรายการที่ **ไม่มีคำลงท้ายหรือคำอธิบายประกอบว่า "สาขา"**
    *   กรณีผู้ใช้เลือกหน่วยงานรหัสสาขา **PC (เช่น PC 10xx, PC 20xx)**: ระบบทำการแสดงรายการรหัสบัญชีเฉพาะรายการที่ **มีคำลงท้ายหรือคำอธิบายระบุว่า "สาขา"** เท่านั้น
*   **ปุ่มเลือกสาขา (Branch Dropdown Specification)**:
    *   ให้ดึงเฉพาะฐานข้อมูลรหัสสาขาที่อยู่ในสถานะ **เปิดใช้งานอยู่ (Active)** มาแสดงผลให้เลือกเท่านั้น
    *   พัฒนาลักษณะของอินเตอร์เฟสให้เป็นแบบ **Dropdown ค้นหาได้ (Searchable Dropdown)** เพื่อให้พิมพ์ตัวย่อหรือรหัสเพื่อกรอกเลือกได้รวดเร็วขึ้น

### 2.5 ระบบสแกนสลิปหลักฐานการคืนเงิน (Refund Slip OCR)
*   สำหรับรายการเคลียร์ยอดที่มีการใช้จ่ายจริงน้อยกว่ายอดเงินทดลองจ่ายเดิม ซึ่งผู้เบิกมีหน้าที่จะต้องโอนเงินส่วนต่างคืนเข้าบัญชีธนาคารบริษัท ให้เพิ่มฟังก์ชันให้ผู้ใช้สามารถอัปโหลดสลิปหลักฐานการโอนเงินคืน (Refund Slip) เข้าสู่ระบบ
*   ระบบต้องทำหน้าที่ในการสแกนสลิปโอนคืนเงินโดยอัตโนมัติ เพื่อตรวจสอบและดึงตัวแปร **วันที่ทำรายการโอน (Transfer Date)** และ **ยอดจำนวนเงินโอน (Refund Amount)** ไปบันทึกแสดงค่าให้อัตโนมัติ

### 2.6 ฟังก์ชันพิมพ์รายงานเอกสารสรุป (AP-3.1 Print out)
*   พัฒนาปุ่มฟังก์ชัน **"Print"** บนหน้าจอสรุปการเคลียร์ยอดเงิน (AP-3.1) เพื่อรองรับการสั่งพิมพ์เอกสารรายงานสรุปผลออกมาเป็นรูปแบบกระดาษอย่างสมบูรณ์ สำหรับให้พนักงานเซ็นกำกับพร้อมใช้ประกอบเป็นหน้าใบปะหน้าในการจัดเรียงใบเสร็จ/ใบรับเงินตัวจริงส่งมอบตรวจสอบตามกระบวนการหลัก

## 3. ระบบเชื่อมโยงข้อมูลหลังบ้าน (ERP Interface & ERP Portal)

### 3.1 สิทธิ์และการปรับแก้ไขข้อมูลหลังการ Interface
*   **สิทธิ์การแก้ไขและยกเลิก**: ในระยะเริ่มต้นของระบบ ให้ใช้กระบวนการทางบัญชีตามมาตรฐานเดิมเป็นหลัก อย่างไรก็ตาม ในฝั่งงานสถาปัตยกรรมระบบให้เริ่มวิเคราะห์กระบวนการ (Workflow/Journey) สำหรับรองรับกรณีที่แผนกบัญชีประสงค์จะแก้ไขหลังจากอินเตอร์เฟสไปแล้ว โดยต้องรองรับวิธีการขอส่งข้อมูลไป **ลบรหัสเอกสาร (Delete Document No.)** ในระบบ ERP แล้วดำเนินการกดส่งแพลตฟอร์มทับซ้ำอีกครั้ง (Overwriting Interface)

### 3.2 โครงสร้างข้อมูลสำหรับอินเตอร์เฟสขาเคลียร์เงิน (Clear Advance ERP Interface Specifications)

| ตัวแปร/ฟิลด์ข้อมูล (Field Name) | เงื่อนไขทางเทคนิคและการแมปข้อมูล (Mapping Logic) |
| :--- | :--- |
| **Posting Date (วันที่โพสต์บัญชี)** | • **กรณีพนักงานโอนเงินคืนบริษัท (Refund)**: ยึดวันที่ทำรายการโอนเงินจริงตามข้อมูลที่ดึงได้จาก Slip หลักฐานการโอน<br>• **กรณีบริษัทจ่ายคืนพนักงาน (Payment)**: ยึดตามวันที่กำหนดจ่ายที่ระบุโดยแผนกการเงินบนส่วนกลางของหน้าจอตรวจสอบ AP-3 |
| **External Document No.** | • บันทึกเป็นข้อมูล **"รหัสพนักงาน" (Employee Code)** ของผู้เบิก |
| **Document Type (ประเภทเอกสาร)** | • ระบุเป็น **`Refund`** สำหรับรายการที่มีเงินส่วนต่างคืนบริษัท<br>• ระบุเป็น **`Payment`** สำหรับรายการที่บริษัทต้องจ่ายเงินคืนพนักงานเพิ่มเติม |
| **Bank Line (รายการบรรทัดธนาคาร)** | • บันทึกรายการลงฝั่ง **Debit (เดบิต)** สำหรับประเภทเอกสารที่เป็น `Refund`<br>• บันทึกรายการลงฝั่ง **Credit (เครดิต)** สำหรับประเภทเอกสารที่เป็น `Payment` |
| **Expense Line (รายการฝั่งค่าใช้จ่าย)** | • ลงบันทึกด้าน **Debit (เดบิต)** ด้วยยอดเงินค่าใช้จ่ายก่อนหักภาษีมูลค่าเพิ่ม (Pre-VAT Expense)<br>• **รูปแบบการกำหนดคำอธิบาย (Line Description Format)**:<br>  `[เลขที่ ADV] + "เบิก" + "เคลียร์เงินทดลอง" + [ชื่อพนักงานที่เคลียร์] + [รายละเอียดเอกสาร]` |
| **Mjus Indicator (ตัวแสดงปรับปรุงบัญชี)**| • ให้ระบุค่าคงที่เป็น **"MS"** เสมอ หากระบบตรวจพบว่าวันที่ในใบเสร็จจริงเกิดขึ้นก่อนหน้าเดือนที่ทำการโพสต์บัญชี (นั่นคือ `Document Date Month < Posting Date Month`) เพื่อใช้ปรับปรุงรายการทางบัญชี |
| **VAT Line (รายการฝั่งข้อมูลภาษี)** | • กรณีที่ใบเสร็จรับเงินมีรายการภาษีมูลค่าเพิ่ม ให้ลงบันทึกในบัญชีภาษีประเภท **"ภาษีซื้อยังไม่ถึงกำหนด"** เป็นค่าเริ่มต้น (Default Account) เสมอ<br>• ส่งออกโครงสร้างชุดข้อมูลรายละเอียดภาษีครบถ้วน:<br>  - `Posting Type`: purchase<br>  - `VAT Code`: wat H (หรือ FBAT ตามเงื่อนไขของแต่ละสาขา)<br>  - `Document Date`: วันที่ระบุตามหน้าใบเสร็จเอกสารจริง<br>  - `Tax ID`: เลขประจำตัวผู้เสียภาษี 13 หลักของผู้ขาย<br>  - `Vendor Name`: ชื่อผู้ประกอบการผู้ขายสินค้า<br>  - `VAT Amount`: ยอดมูลค่าเงินภาษีจริงตามเอกสาร |
| **Withholding Tax & Clear Advance Line** | • **ข้อกำหนดทางบัญชี**: กำหนดให้ระบบส่งข้อมูลยอดเงินภาษีหัก ณ ที่จ่าย (WHT) และข้อมูลบรรทัดล้างเวนเดอร์คู่ค้างเดิม (Clear Advance Vendor Account) เป็น **ค่า 0 บาท เสมอ** ไปยังระบบ ERP เพื่อแยกขั้นตอนให้ผู้ดูแลบัญชีใช้ฟังก์ชันในระบบหลักดำเนินการล้างเวนเดอร์และจับคู่ยอดด้วยมืออย่างโปร่งใส<br>*(หมายเหตุ: บนหน้าจอตารางตรวจสอบก่อนคลิกส่งอินเตอร์เฟส ยอดผลรวมสองด้าน (Debits/Credits) จะไม่สมดุลกัน (Unbalanced) ถือเป็นสถานะปกติตามเงื่อนไขนี้)* |

## 4. หน้าจอ ERP Portal และตัวกรองระบบแสดงรายงาน (Reports & Dashboards)

### 4.1 ฟังก์ชันบนหน้าจอตรวจสอบก่อนส่ง Interface (ERP Portal Preview Screen)
*   **การจัดการกลุ่มรายการ (Batch Actions)**: พัฒนาให้ระบบรองรับการคลิกเลือกทำรายการแบบหลายรายการพร้อมกันได้ (Batch Approval / Batch Send to ERP Interface) เพื่ออำนวยความสะดวกในการจัดส่งข้อมูลปริมาณมากๆ
*   **แก้ไขวันทำจ่ายได้ยืดหยุ่น (Inline Edit Payment Date)**: ยินยอมให้เจ้าหน้าที่การเงินสามารถคลิกแก้ไขหรืออัปเดตวันทำจ่าย (Payment Date) บนแถวข้อมูลพรีวิวได้อีกครั้ง ก่อนที่จะกดยืนยันจัดส่งข้อมูลเข้าสู่ Interface
*   **ระบบคัดแยกตัวกรอง (Status Filtering)**: พัฒนาปุ่มตัวกรองเพื่อแยกสถานะความต้องการอย่างเป็นเอกเทศระหว่างชุดข้อมูล:
    *   `Pending` (รายการที่รอส่งข้อมูลอินเตอร์เฟส)
    *   `Sent` (รายการที่ทำขั้นตอนการอินเตอร์เฟสเข้า ERP สมบูรณ์แล้ว)

### 4.2 ระบบรายงานสำหรับตรวจสอบของแผนกบัญชี (Accounting Report Filters)
*   **ระบบตรวจสอบตัวกรองสองชั้น (Nested/Multi-Column Filters)**:
    *   พัฒนาความสามารถของตารางรายงานให้พนักงานสามารถทำการค้นหาและกรองค่าระบุหลายๆ ตัวแปรพร้อมกันได้ เช่น การค้นหารหัสพนักงานเฉพาะบุคคลร่วมกันกับการเจาะระบุช่วงสัปดาห์วันจ่ายเงิน
*   **ตัวกรองตรวจสอบการส่งเงินล่าช้า (Aging & Overdue Monitor Filter)**:
    *   เพิ่มระบบการเลือกรายงานสำหรับคัดกรองข้อมูลรายการเบิกจ่ายเงินทดลองที่ **ยังไม่ได้รับการอนุมัติเคลียร์เงิน (AP-3 Status <> Cleared)** และมี **วันที่กำหนดเคลียร์เงินล่วงเลยมากกว่าวันปัจจุบัน (นั่นคือ `Clearing_Date < Current_Date`)** เพื่อให้ฝ่ายบัญชีใช้เป็นเครื่องมือหลักในการดึงรายการออกมาตรวจสอบและทำเรื่องทวงถามและติดตามเงินทดลองจ่ายค้างส่งได้
*   **การแสดงปีระบบตามเกณฑ์มาตรฐานสากล**:
    *   ปรับโครงสร้างหน้าจอปฏิทิน ระบบการกรอกข้อมูล และเอกสารสรุปผลรายงานทั้งหมดให้แสดงผลสัญลักษณ์ปีเป็น **คริสต์ศักราช (ค.ศ. / คริสตศักราช)** แทนการใช้ พ.ศ. เพื่อลดความสับสนในการใช้งานซอฟต์แวร์ต่างระบบ
